邀请注册改造计划

必须使用注册码注册，关闭随机注册入口

本文档用于冻结邀请注册方案，作为后续实现、测试与验收的唯一参考。目标是把现有账号注册收口为“必须输入一次性邀请码”，并同步补齐后台管理与游客入口收束。

状态：计划冻结前版本 范围：后端 / 前端 / 管理后台 约束：一次性邀请码
1. 目标

把注册改成“邀请制”，不再支持随机注册

当前系统的注册入口只需要昵称和密码，且还存在游客登录自动创建账号的路径。改造后，任何新账号都必须由管理员发放的邀请码完成注册，避免随意注册和账号泛滥。

核心结果： 普通用户无法绕过邀请码直接注册；邀请码成功使用后立即失效；游客登录不再创建新账号。
2. 冻结 Specs

本次必须达成的验收点

  • 注册接口必须校验 registration_code，缺失直接拒绝。
  • 邀请码为一次性使用，注册成功后即标记为已使用。
  • 游客登录保留路由，但不再创建用户，统一返回 403。
  • 后台提供邀请码的生成、列表、禁用能力。
  • 前端注册页必须显示邀请码输入框，并能在手机上清晰操作。
3. 非目标

本期不做的事

  • 不做开放式自助注册。
  • 不做复杂的多次使用邀请码策略。
  • 不做邀请码前台公开领取页面。
  • 不改现有登录方式，只收紧注册路径。
4. 接口契约

后端与前端的调用约定

接口 / 组件 输入 输出 / 行为 错误与约束
POST /api/auth/register nickname、password、registration_code 成功后返回 token 与用户信息 缺码 400；无效/已用/已禁用 403；昵称重复 409
POST /api/auth/guest 无 不再创建随机账号 固定返回 403，提示游客注册已关闭
GET /api/admin/registration-codes 管理员 JWT 邀请码列表 非管理员由现有 admin middleware 拦截
POST /api/admin/registration-codes 生成数量、备注等管理参数 创建一次性邀请码 管理员权限必需
PUT /api/admin/registration-codes/{id}/disable 邀请码 ID 禁用未使用的邀请码 已使用码不可再变更为可用
apiClient.register() 昵称、密码、注册码 发送注册请求 前端必须同步更新请求体结构
5. 数据模型

邀请码表的职责

  • 保存邀请码本身和使用状态。
  • 记录创建时间、使用时间、创建人和使用人。
  • 支持一次性消耗，避免并发重复注册。
  • 支持后台列表查询和禁用。
6. 前端改动

注册页与管理页都要改

  • 注册页新增“注册码”输入框，必须填写。
  • 错误文案要短、明确、适合老人识别。
  • 后台新增邀请码管理页面，可生成、复制、查看、禁用。
  • 页面在手机宽度下不能出现拥挤或被裁切的情况。
7. 测试计划

按契约先测，再实现

测试范围 要覆盖的场景 验收标准
后端注册 缺码、错码、已用码、成功注册、并发消耗同一码 所有分支返回稳定且符合约定的状态码与错误信息
游客入口 调用 /api/auth/guest 始终返回 403，不产生新账号
后台接口 邀请码生成、列表、禁用、权限校验 管理员可操作，普通用户被拦截
前端请求 apiClient.register 请求体字段校验 请求中必须带上 registration_code
8. 实施顺序

先后顺序要固定

  • 先定后端数据模型和接口契约。
  • 再写测试用例，覆盖一次性邀请码和游客关闭路径。
  • 再改后端注册与后台邀请码接口。
  • 最后改前端注册页和管理员页面。
9. 默认假设

没有额外说明时按这个执行

  • 邀请码由管理员后台生成，不开放给普通用户。
  • 邀请码第一版只做一次性使用，不做多次复用。
  • 保留游客接口路径，避免兼容性断裂，但它不再创建账号。
10. 验收结论

通过标准

只要以上契约、测试和界面都完成，且注册链路无法在没有邀请码的情况下新增账号，就可以认为这次改造达标。

最终要求： 用户注册时只能走邀请码；游客注册不再可用；后台能管理邀请码生命周期；前端移动端显示清晰可用。
